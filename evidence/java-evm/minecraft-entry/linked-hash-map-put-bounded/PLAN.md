## Proposed guest implementation

Preserve `HashMap.java` (including private-final `HashMap.Node`), its accepted node and unordered `EntrySet`/iterator, and every existing class image except `LinkedHashMap` image 113. Recompile Java 8 `-g:none` source only for the changed image and at most three newly appended ordinary guest helper images:

1. `LinkedHashMapEntry<K,V>`: genuine `Map.Entry` key/value fields and next link, providing actual stable entry references in insertion order. `getKey`, `getValue`, and a real `setValue` (return old value, replace only the value, no structural count change) are ordinary guest Java. Entry `equals` remains unbound unless separately proven necessary; do not fabricate equality.
2. `LinkedHashMapEntrySet<K,V>`: cached live `Set<Map.Entry<K,V>>` view over the owning map's head/tail chain, with ordinary `size`, `isEmpty`, and `iterator`. Keep unsupported mutators/array-free overloads explicitly unbound. Implement only the already-profiled typed `toArray(T[])` fit behavior: null-target NPE, short-target raw refusal before writes, fitting target gets the same array, first trailing slot null and later tail untouched; ordinary array-store/ArrayStoreException semantics are not hidden.
3. `LinkedHashMapEntryIterator<K,V>`: independent cursor and expected structural modification count, `hasNext`, and Java-order `next` behavior (CME check then NSEE); no iterator removal.

Change only `LinkedHashMap.java` otherwise. Preserve its existing Java 8 constructor, inherited `HashMap` state/`size`/`modCount`, `accessOrder == false`, and public erased `put(Object,Object):Object` dispatch. Add subclass-owned head/tail and cached-view state for a real linked-entry backend; override `put`, `entrySet`, and `hashCode`. This backend deliberately does **not** claim to populate or resize the inherited `HashMap.table`, and inherited hash-bucket iteration remains untouched. It exposes actual guest `Map.Entry` references and ordered live iteration, rather than returning a fake or unordered view.

### `put` semantics and mutation ordering

- Accept null keys and values. Compute the incoming key hash once (`0` for null; otherwise call its real guest `hashCode`) and apply Java 8's spread transform. Do this before map writes.
- Search in insertion order. A match requires equal spread hash and either key identity or `incomingKey.equals(existingKey)`; do not use Object identity/hash constants as substitutes and do not reverse the `equals` direction. A callback refusal/guest exception is propagated honestly, not converted into a result.
- For a matching key, return the prior value and update the **same** entry node's value. Preserve its first insertion position and do not change `size` or `modCount`.
- For a new key, allocate its entry before linking or changing inherited counters; append at tail, increment inherited `size` and `modCount` once, and return null. Allocation/callback failure must not publish a partial insertion.
- Handle collision-capacity/treeification boundaries with an explicit finite profile policy: if a supported bound would be exceeded, refuse before mutating. Do not silently skip JDK comparable/treeification callbacks or fall back to a false miss. The concrete entry bound and a preflight that accounts for both existing global object limits and helper allocations must be agreed at design approval; this plan does not alter any global quota.

### Hash and deliberately unsupported surfaces

Implement ordinary `Map.hashCode` as a sum over real entries of `(keyHash ^ valueHash)`, treating null as zero and invoking real guest callbacks. Thus the empty map key hashes to zero naturally; nonempty maps are content-based. No new native binding is proposed. A callback the runtime cannot execute remains an honest raw refusal or genuine guest exception. `Map.equals`/`HashMap.equals` remains unbound (no identity shortcut). Unsupported inherited data APIs such as get/remove/clear/contains/getOrDefault/putAll, access-order operations, and full-map equality/clone/serialization remain outside this capability and must not be represented as newly supported. The fact that this backend is distinct from inherited buckets must be documented; callers cannot infer bucket-state consistency from `table`.

`entrySet` is cached and live. Each iterator has its own cursor and captures `modCount` at construction. Existing-value overwrite is visible through the same entry but does not make an iterator fail fast; insertion changes `modCount`, and `next` then throws CME. Exhaustion throws NSEE. The existing typed-array fit profile is retained as described above. `Entry.setValue` is proposed as genuine ordinary node behavior, not a fake native success; this method still needs a focused oracle/EVM gate before acceptance.

## Risks requiring approval/measurement

- Subclass-owned backend creates a real divergence from inherited `HashMap.table`; any accidental inherited operation would observe stale/empty bucket state. Keep the refusal boundary explicit and test raw refusal before mutation.
- Guest callbacks can throw, refuse, or reenter. Ordering and atomicity must be verified; unsupported callback behavior may not be converted into false insertion/lookup results.
- Helper images consume class slots and heap/object quota; array-backed or unbounded alternatives are not assumed safe. Approve exact helper count and a preflight bound before coding.
- Private `HashMap.Node` must remain untouched; attempting protected hooks, compiler-stub relaxation, or a generic-engine change requires a separate review.
- Entry `setValue`, typed-array ArrayStoreException behavior, and cross-profile `Map.hashCode` callback reachability require concrete, generated probes before acceptance.
